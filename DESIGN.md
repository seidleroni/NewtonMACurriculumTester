# Newton Math — Design & Specification

A local-first daily math practice app for two kids, grounded in the Newton, MA elementary
math curriculum. Built to be used 5–10 minutes per day, to adapt to each kid, to make
progress visible, and to be **fully self-tested** (no manual QA).

> Status: **SPEC — pending approval.** No application code is written yet. This document is
> the thing to review. The "first slice" build (Phase 0) begins only on your go-ahead.

---

## 1. Goals & constraints

**Who.** Two profiles:
- **Jacob** — finishing Grade 1 → starts on **Grade 2** content.
- **Samuel** — finishing Grade 3 → starts on **Grade 4** content.

**What.** Each kid gets a short daily session (~10–15 problems, ~7 min) pulled adaptively
from their grade's skill map. The app teaches (short lessons + hints), tests (auto-generated,
auto-graded problems), tracks mastery per skill, resurfaces weak skills via spaced
repetition, and shows progress to both the kid and the parent.

**Hard constraints (from you):**
- **Local-first.** Runs on the family computer via a single `uv run` command. No login —
  a "pick your face" screen. Architected so it *can* deploy to the web later with little rework.
- **Simple & sturdy UI.** Server-rendered HTML + HTMX. Minimal JS. Keyboard-first
  (type the answer, press Enter). Stars / level-ups / progress bars for engagement.
- **Python, everything via `uv`.** `uv run` for the app and tests; `uv add` for deps.
- **Git-controlled** from the first commit.
- **Self-tested without your intervention.** `uv run pytest` must be green; the answer
  generators/graders are verified exhaustively (property-based), not spot-checked.
- **Math first.** Grades 2–4. Literacy and higher grades reuse the same engine later.

**Explicit non-goals (for now):** accounts/auth, cloud sync, multiplayer, sound/voice,
mobile-native apps, AI at runtime (all teaching content is authored ahead of time and baked in),
and **day-streak gamification** — we practice only on school nights, so a "🔥 N-day streak" that
breaks every weekend/holiday would misfire and discourage. Progress is shown as **skills
mastered, level-ups, and accuracy/speed trends** instead (signals that only ever go up).

## 2. Curriculum grounding

Newton's K–5 core program is **Investigations 3 (TERC)**, supplemented by ST Math, Khan
Academy, and Savvas/Pearson digital access. Investigations aligns to the **2017
Massachusetts Curriculum Framework for Mathematics** (which tracks Common Core almost
exactly). The MA framework — not the Investigations *unit names* — is the right backbone,
because it is the precise, enumerable, testable skill list. Each skill below carries its
**MA/CCSS standard code** (e.g. `2.NBT.A.1`) so it maps cleanly back to what Newton teaches.

The single most important design fact, from the research pass: **~85–90% of Grades 2–4 math
can be generated and graded by pure deterministic Python — no AI, no internet at runtime.**
The remainder is handled by image assets (Phase 3) or multiple-choice/parent fallbacks
(Phase 4). See the full catalog in §10.

## 3. Architecture overview

```
Browser (HTMX)  ──HTTP──►  FastAPI app  ──►  Skill engine (pure Python, deterministic)
   Jinja2 HTML  ◄────────  (routes)     ──►  Mastery + Scheduler (pure Python)
                                        ──►  SQLite (per-kid state, attempts, sessions)
```

- **No runtime AI / no network.** Problems are generated by seeded Python functions; lessons
  and hints are authored text baked into the code. The running app works fully offline.
- **Pure functional core.** Generators, graders, mastery scoring, and scheduling are pure
  functions of `(state, seed)`. This is what makes the app exhaustively testable.
- **Thin web shell.** FastAPI + Jinja2 render HTML fragments; HTMX swaps them in. The server
  holds all logic; the browser holds almost none.

| Concern | Choice | Why |
|---|---|---|

## 4. The skill engine

The heart of the app. Each skill is a small, self-contained, deterministic unit.

```python
@dataclass(frozen=True)
class Problem:
    skill_id: str          # "2.NBT.B.5"
    level: int             # difficulty 1..max_level
    prompt: str            # "47 + 38 = ?"
    answer: Answer         # canonical correct answer (typed, see §5)
    payload: dict          # extra data for rendering (operands, image ref, choices)

class Skill:
    id: str                # standard code, e.g. "2.NBT.B.5"
    slug: str              # url/file-safe, e.g. "g2-add-sub-100"
    grade: int             # 2 | 3 | 4
    domain: str            # "Number & Operations in Base Ten"
    title: str             # kid-facing name, e.g. "Add & subtract within 100"
    max_level: int         # how many difficulty tiers (2–4)
    answer_type: str       # which Answer subtype (see §5)
    prereqs: list[str]     # skill ids that should come first
    phase: int             # build phase 1–4 (see §10 / §12)

    def generate(self, level: int, rng: random.Random) -> Problem: ...
    def lesson(self) -> Lesson: ...                       # short authored teaching card
    def hints(self, p: Problem) -> list[str]: ...         # escalating hints for a problem
    def worked_example(self, p: Problem) -> str: ...      # step-by-step for THIS problem
```

**Determinism is mandatory.** `generate` takes an injected `random.Random`. Same seed →
same problem. This is what lets the test suite generate thousands of problems and assert
every one is internally consistent (its declared `answer` actually grades correct, and its
numbers respect the skill's invariants — e.g. never a negative subtraction for Grade 2).

**Difficulty levels** let a single skill span a range. Example for `2.NBT.B.5`
(add/subtract within 100): L1 = no regrouping; L2 = regrouping; L3 = mixed +/− with
regrouping under a soft time target. The kid's *current level* on a skill is tracked in
their state (§6) and drives `generate`.

**Registry.** All skills register themselves into a global `REGISTRY: dict[str, Skill]`.
Per-kid grade selection just filters the registry by `grade`.

## 5. Answer types & grading

Every answer is a typed object with a single job: decide if the kid's raw text input
matches, after sensible normalization. All grading is deterministic and returns
`GradeResult(correct, expected_display, given_display, note)`.

| Answer type | Accepts / normalizes | Used by (examples) |
|---|---|---|
| `IntegerAnswer` | strips commas, spaces, trailing units ("85 apples"→85) | most arithmetic |
| `FractionAnswer` | `a/b`; accepts reduced/unreduced + mixed↔improper (`3 1/4`==`13/4`) | all fractions |
| `DecimalAnswer` | `0.7`==`0.70`; tolerant of leading/trailing zeros | decimals |
| `ComparatorAnswer` | one of `<` `=` `>` (also accepts words "greater") | comparing numbers |
| `TimeAnswer` | `HH:MM`, am/pm; normalizes `3:05`/`3:5` | telling time, elapsed time |
| `MoneyAnswer` | `$1.04` / `104¢` / `1.04` → integer cents | money problems |
| `SequenceAnswer` | comma/space-separated terms; exact ordered match | skip-count, patterns |
| `SetOfPairsAnswer` | order-insensitive set of pairs (`1x24`,`2x12`,…) | factor pairs |
| `BooleanAnswer` | yes/no, odd/even, prime/composite | classification |
| `TextLookupAnswer` | case/whitespace-insensitive; synonym sets (fourths≡quarters) | shape names |
| `ChoiceAnswer` | id of selected option | multiple-choice fallbacks |

Grading never depends on exact string formatting of the kid's input — only on value.
This is heavily tested (§11): for each type, a battery of equivalent forms must all grade
correct and a battery of near-misses must all grade incorrect.

## 6. Mastery model (per kid × skill)

Goal: a single interpretable **0–5 star** rating per skill that (a) can't be maxed by only
doing easy problems, (b) rewards consistent correctness and speed, and (c) recovers
gracefully from a bad day.

**State stored per (kid, skill):**
`score` (0.0–1.0), `level` (current difficulty), `box` (Leitner 1–5, see §7),
`due_at` (date), `attempts`, `correct`, `consec_correct` (a *correct-answer* run used to gate
level-ups — not a calendar streak), `avg_response_ms`, `introduced_at`, `mastered_at`, `last_seen_at`.

**Scoring (`mastery.py`).** `score` is an exponential moving average pulled toward a
**ceiling that depends on the difficulty level you're succeeding at**:

```
level_ceiling(L) = L / max_level          # only top-level success can reach 1.0
on correct at level L:
    target = level_ceiling(L)
    if target > score:  score += ALPHA * (target - score)   # ALPHA≈0.30, +bonus if fast
    else:               score += SMALL_GAIN * (1 - score)   # small reward, already above
on wrong:
    score -= ALPHA * PENALTY * score        # PENALTY≈0.5; gentle, clamped ≥ 0
```

**Level promotion / demotion:**
- Promote (L→L+1) when `consec_correct ≥ 3` AND `score ≥ level_ceiling(L) − ε`, then advance
  the Leitner box. Reset `consec_correct`.
- Demote (L→L−1, never below 1) when the last 5 attempts are <40% correct, and drop one box.
  Demotion is quiet — no penalty messaging to the kid.

**Stars (display):** `stars = clamp(floor(score * 5), 0, 5)`. A skill is **"mastered"**
(badge + stops being introduced as a focus) when `score ≥ 0.95` at `max_level`.

All constants live in one place and are tunable; the *shape* (ceiling-by-level, gentle
penalty, streak-gated promotion) is the spec. Fully unit-tested with scripted attempt
sequences (§11).

## 7. Spaced repetition & the daily session

### 7.1 Leitner spacing (`scheduler.py`)
Each skill sits in a **box 1–5** with review intervals in days:
`box1=1, box2=2, box3=4, box4=7, box5=15`. A skill is **due** when `due_at ≤ today`.
- Correct review → `box = min(5, box+1)`, `due_at = today + interval[box]`.
- Wrong → `box = max(1, box−1)`, `due tomorrow`.
- Newly introduced skill → box 1, due today.

### 7.2 Introducing new skills (the "learning edge")
Each grade has an **ordered skill sequence** (roughly standard order + prerequisites). The
kid starts with the first 1–2 skills *introduced* and the rest *locked*. A new skill is
introduced (and triggers its **lesson card**) when the kid's current focus skill reaches
`level ≥ 2` / `score ≥ 0.5` AND the kid has `< 4` active-unmastered skills (so we never pile
on). Prereqs gate introduction (e.g. multiplication facts before two-step word problems).

### 7.3 Composing one daily session (~12 problems, capped at the daily goal/time)
For the kid's active pool:
1. **Due reviews** — up to ~5, most-overdue and lowest-score first.
2. **Focus** — ~5 problems on the current learning-edge skill at its current level (adaptive:
   bumps a level mid-session after a short correct streak, eases after misses).
3. **Stretch** — 1–2 problems one level harder, or a peek at the next skill to be introduced.
4. **Fill** — remaining slots from the weakest active skills.

Problems are **interleaved** (not clustered by skill — interleaving improves retention) and
the session ends at the daily goal (default 12 problems / ~7 min, configurable per kid).
Wrong answers re-queue that skill for one more attempt later in the session.

### 7.4 Placement
Default is a gentle ramp from the start of the grade. Optional (Phase 1+) lightweight
**probe**: on introducing a skill, 1–2 quick questions; acing them seeds a higher initial
level so a kid who already knows it isn't bored.

## 9. Teaching: how each skill is taught

**Principle.** I author every lesson, hint, and worked example *ahead of time* and bake it
into the skill — no live AI at runtime. The teaching follows the **strategies Newton/Investigations
actually use** (decompose by place value, equal groups & arrays, number lines, area models,
benchmark fractions) rather than just stating rules, because that's what builds understanding
and matches what the kids see in class. All of this text lives in plain files you can read and
edit — so where my wording isn't right for your kid, you can tweak it (or hand a skill to me to
redo).

**Three touchpoints per skill** (the `lesson() / hints() / worked_example()` methods from §4):

1. **Lesson card** — shown once when a skill is first introduced, re-openable anytime from the
   dashboard. 2–4 sentences of kid-language explanation + one worked example + the key strategy.
   ~20–40 seconds to read. The kid presses "Got it" to start.
2. **Escalating hints** — on a wrong answer, reveal Hint 1 (a nudge toward *where to look*), then
   Hint 2 (the strategy / first concrete step) if still stuck. Hints never just give the answer.
3. **"Show me how" worked example** — generated for the *exact* problem the kid missed: the same
   numbers walked through step-by-step using the taught strategy. It's a per-skill template filled
   with that problem's live values, so it's always specific, never generic.

The honest part: some standards are about *open reasoning* ("explain why…") or *physical action*
("measure the table"). Those can't be auto-graded, so I **teach the concept the same way** but
change how it's *assessed* — into multiple-choice or an optional parent-checked task. Below are
five real examples spanning the full range; this is shippable content, not placeholder.

---

### A. Procedure — `2.NBT.B.5` Subtract within 100 with regrouping (Jacob)

> **Lesson card.** "When you subtract, stack the tens and ones. If the top ones digit is too
> small, you **regroup**: trade 1 ten for 10 ones so you have enough. Example: **62 − 47**. Ones
> first: 2 − 7 won't work, so take 1 ten from the 6 (now it's 5) and give it to the ones (2 becomes
> 12). Now 12 − 7 = **5** ones, and 5 − 4 = **1** ten → **15**. 💡 *Not enough ones? Trade a ten.*"
>
> **Hints** (for 62 − 47): ① "Start with the ones. Can you do 2 − 7? If not, you need to regroup."
> ② "Borrow 1 ten: the 6 becomes 5, and the 2 ones become 12. Now do 12 − 7."
>
> **Show me how** (62 − 47): `6|2  −  4|7` → "12 − 7 = 5 ones" → "5 − 4 = 1 ten" → "**15**".

### B. Concept — `4.NF.A.2` Compare fractions with unlike denominators (Samuel)

> **Lesson card.** "To compare fractions you need **same-size pieces**. Two tricks: (1) **Benchmark
> ½** — is each fraction more or less than a half? (2) **Common denominator** — rename both with the
> same bottom number, then just compare the tops. And remember: a *bigger bottom number means
> smaller pieces*."
>
> **Hints** (for 3/5 vs 2/3): ① "Try comparing each to ½, or find a common denominator for 5 and 3."
> ② "Use fifteenths: 3/5 = 9/15 and 2/3 = 10/15 — now compare 9 and 10."
>
> **Show me how** (3/5 ? 2/3): "Common denominator 15. 3/5 = **9/15**, 2/3 = **10/15**. 9 < 10, so
> **3/5 < 2/3**." *(Phase 2 adds two stacked fraction bars so the kid can also see it.)*

### C. Needs a picture — `2.MD.C.7` Tell time on an analog clock (Jacob, Phase 2)

> **Lesson card** (with a generated clock face showing 3:40). "The **short hand** points to the
> **hour**. The **long hand** points to the **minutes** — count by 5s around the clock (the 1 means
> 5, the 2 means 10, the 8 means 40…). Here the short hand is just past 3 and the long hand is on
> the 8 → 8 × 5 = 40 → **3:40**."
>
> **Hints**: ① "Which hand is short? That's the hour." ② "The long hand is on a number — count by 5s
> from the 12 to get the minutes."
>
> **Show me how** narrates the *specific* generated clock the kid saw. The image is drawn
> deterministically in Python (same time → same picture), so the worked example always matches.

### D. Word problem & reasoning — `4.OA.A.3` Multi-step + interpret the remainder (Samuel)

> **Lesson card.** "Some problems take **two steps** — do them in order. And when you divide, the
> **leftover (remainder) has a meaning**: sometimes you round **up**, sometimes you drop it,
> sometimes the leftover *is* the answer. Ask yourself: *what does the leftover mean here?* Example:
> 150 kids, each bus holds 36. 150 ÷ 36 = 4 remainder 6. Those 6 kids still need a seat → round
> **up** to **5 buses**."
>
> **Hints**: ① "First do the division. Then ask what the leftover stands for." ② "You can't leave 6
> kids behind — they need a bus too. So round up."
>
> **Show me how** (this problem's numbers): "150 ÷ 36 = 4 R6. 6 kids left over still need a ride →
> **5 buses**."

### E. Open reasoning, reframed — `2.NBT.B.9` "Explain why a strategy works" (Phase 4)

This standard asks the kid to *justify*, which has no single gradeable string. So I **teach the
why** the same way but **assess it as multiple-choice**:

> **Lesson card.** "Adding is easier when you break numbers into tens and ones. 28 + 35 → add the
> tens (20 + 30 = 50), add the ones (8 + 5 = 13), then put them together (50 + 13 = 63). It works
> because tens always add with tens and ones with ones."
>
> **On-screen item (auto-graded).** "Which is the *best* reason 28 + 35 = 63?"
> ○ "Because you add the tens (50) and the ones (13) and combine them." ✓
> ○ "Because 28 and 35 are both close to 30." ○ "Because you count up by ones from 28." (plausible
> distractors)
>
> **Optional parent version.** A side prompt — "Ask Jacob to say *why* out loud" — that you can
> thumbs-up. Fully optional; the auto-graded multiple-choice carries the daily loop on its own.

**Coverage:** every Phase-1 skill ships with all three touchpoints; Phase-2/3 skills add the image
to the lesson and worked example; the handful of Phase-4 reasoning/hands-on skills use the
reframe pattern in (E). I can write all of this — flag any skill where you'd rather author the
explanation yourself.

## 11. Testing strategy (no manual QA)

The point of the pure-functional core is that correctness is *provable by the suite*, not by
me clicking around. Target: `uv run pytest` green, meaningful coverage on the core.

1. **Generator self-consistency (Hypothesis, the key test).** For every registered skill, for
   each level, for thousands of seeds: generate a problem and assert
   `grade(problem, problem.answer).correct is True`, plus skill invariants
   (no negative results in Grade 2 subtraction; operands within the standard's range; division
   is whole unless remainders are intended; fractions use only grade-allowed denominators).
   This single parametrized test guards every skill we ever add.
2. **Answer grading edge cases.** Per answer type: a table of equivalent forms that must all
   grade correct (`3 1/4`==`13/4`, `$1.04`==`104¢`, `0.7`==`0.70`) and near-misses that must
   grade incorrect.
3. **Mastery logic.** Scripted attempt sequences → assert promotion after a correct streak,
   gentle recovery after misses, ceiling-by-level (you can't 5-star with only L1), and the
   mastered threshold.
4. **Scheduler logic.** Assert due-selection ordering, session composition ratios, the
   "introduce a new skill" gate (prereqs + active-load cap), and interleaving.
5. **Endpoint/integration (TestClient).** Full daily loop against a temp SQLite db: pick kid →
   play → submit right/wrong answers → state persists → summary renders → dashboards render.
6. **Determinism.** Same seed ⇒ identical problem; DB writes are idempotent per attempt.

CI-style local gate: a `uv run` task that runs `ruff check` + `pytest`. Optional GitHub
Actions later (it's the same command).
